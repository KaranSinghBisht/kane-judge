The loop

  1. Read. Kane itself lists the use-cases your README promises (kane-cli context ingest). Every one has to be accounted for.
  2. Test. Claude writes one plain-English Kane flow per claim, and Kane runs them in real Chrome, four at a time.
  3. Investigate. For every failure: is the product broken, was the test wrong, or is it blocked? Every pass is checked against Kane's own screenshot.
  4. Fix. The agent fixes your code, or takes a promise you never built out of the README. Kane re-runs the same flow, unchanged.
  5. Gate. Kane's verdict engine judges the sealed evidence pack with self-healing off. The flows stay behind as a pre-push and CI gate.

It checks Kane too

A judge built on a test runner has to distrust its passes. Measured on Kane CLI 0.10.5, against a page whose Total row is hidden with display:none:

The check, and how it was runFresh runsPassed (wrong)
"Verify the Order summary shows a Total row with the amount $47.00", default mode41
The same, with --assertion-mode visual32
A replay of a run that had recorded a pass44
Reworded: "visibly displayed … (not merely present in the page's HTML)"60
A flow with no steps at all, testrun run33

So Kane Judge refuses a check that doesn't say what is visibly shown, refuses a flow without steps, needs a passed assert step in the evidence pack before a claim counts as proven, and has the agent open Kane's screenshot for every pass. The write-up and every transcript.
